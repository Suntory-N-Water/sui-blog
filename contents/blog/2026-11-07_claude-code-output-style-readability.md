Claude Code に質問すると、私は返答を読んだあとに「簡潔に説明をお願いします。要するにどういうことですか。」と打ち返すことが続いていました。ちいかわのモモンガの「食べたいんだよォー」と同じ調子で、「何言ってんのかわかんねえんだよォー」と叫びたくなる状態です。

この記事では、自分の会話記録から読めなかった返答の傾向を集め、Claude Code の出力スタイルを書き直した結果を紹介します。同じ質問への返答は、既定の設定で 34 行だった返答が、書き直した出力スタイルで 9 行になりました。

## 読めなかった返答の傾向

Claude Code は、会話の記録をプロジェクトごとに JSONL のファイルとして `~/.claude/projects/` に保存しています。私はこの記録から、2026 年 10 月 4 日から 11 月 3 日までに私が送った発言を抜き出しました。「分からない」「要するに」「長い」などの語を含み、直前に Claude Code の返答がある発言は 95 件ありました。

95 件のうち 38 件は、「要するに」「簡潔に」「長い」を含む発言です。この 38 件の直前の返答は、行数の中央値が 16 行でした。38 件には、Claude Code が 1 文目で質問に答えていた返答も含まれます。テストが必要かを聞いた私に、Claude Code は 1 文目で「要りません」と答えたうえで、見出し付きの説明を 28 行続けました。28 行を読み終えた私は、「ごめん、よくわかんねえ。既存のテストがいらねえってこと？」と聞き直しました。

私が読めなかった返答には、長さのほかに、前の返答で付けた見出しや番号で中身を指す書き方もあります。飲み物のカードに描いたマグカップの位置を直す作業で、Claude Code は前の返答に 2 つの直し方を書き、次の返答では「前回の 2 つ」という見出しの下に同じ 2 つを並べました。私は前の返答の 2 つの直し方を覚えていなかったので、「前回の 2 つ」が何を指すのか分からず、「わかんねーよ」とだけ返しています。

比喩や Claude Code が作った語も、読めない原因になっていました。文字起こしの作業を再現できるかを聞いたとき、Claude Code は「全工程を順に動かす入口と手順書がありません」と答えています。私は「入口」が全工程を 1 回で実行するスクリプトを指すと読み取れず、「入口と言われても分からない。比喩表現は全て通じません」と返しました。セキュリティの調査結果を報告した返答も、最後に「この指摘の修正パッチを作りますか？」と聞いていて、私は「修正パッチって言葉の意味がわかんない」と書いてから修正を頼んでいます。

## 出力スタイルに書いたルール

出力スタイルは、Claude Code がセッション中のすべての返答に使う指示を Markdown で書いたファイルです。`~/.claude/output-styles/` に置き、`settings.json` の `outputStyle` に名前を指定すると使われます。

返答の組み立て方には、倉島保美氏の『改訂新版 書く技術・伝える技術』の 7 つの法則を使いました。倉島氏は東洋経済オンラインの記事で、7 つの法則を次のように挙げています。

1. 文章の冒頭には重要な情報をまとめて書く
2. 詳細はパラグラフを使って書く
3. パラグラフの冒頭には要約文を書く
4. 文頭にはすでに述べた情報を書く
5. 並列する情報は同じ構成・同じ表現で書く
6. 1つの文には、1つのポイントだけを書く
7. 無駄なく、簡潔に書く

私はこの 7 つに、会話記録で見つけた傾向への対策を足しました。1 文目で質問に答えること、返答を 10 行以内にすること、前の返答を番号で指さずに中身を書き直すこと、関数名や比喩ではなく中身の分かる名前で書くことの 4 つです。

返答を短くする方法には、Kazuki Ota 氏が Zenn で公開した explain-before-shorten というスキルの考え方を使いました。このスキルは、言葉だけを削るのではなく、説明で扱う話題を絞って文章を短くするよう指示しています。私は出力スタイルに「短くするときは、語を削らずに扱う話題を減らす」と書きました。

Anthropic の公式ドキュメントからは 2 つを取り入れました。Opus 5 向けのプロンプトのページは、Opus 5 の返答は以前のモデルより長く、effort を下げても短くならないため、短くするよう明示的に指示する必要があると書いています。同じページは、長い指示の末尾に短い念押しを置くことも勧めています。プロンプトのベストプラクティスのページによると、例を示すことは出力の形をそろえる最も確実な方法の 1 つです。私は出力スタイルの末尾に、単純な質問への模範解答を 1 つと、1 文目と行数を確かめる念押しを置きました。

書き直した出力スタイルの全文は次のとおりです。`keep-coding-instructions: true` は、Claude Code に組み込まれたソフトウェア開発の指示を残したまま、返答の書き方だけを変える設定です。「誰が何をどうするかを省略しない」の節は、このブログの執筆ルールから写しています。

```markdown ~/.claude/output-styles/sui-style.md
---
name: sui-style
description: 書く技術・伝える技術の 7 つの法則と、ユーザーが過去に「分からない」と指摘した返答の傾向を元にした、短く結論から書く文章ルール
keep-coding-instructions: true
---

# 読み手の前提

ユーザーは前の返答の中身を覚えていない。1 回の返答で読めるのは 10 行程度まで。この 2 つを前提に書く。

# 返答の組み立て

倉島保美『書く技術・伝える技術』の 7 つの法則に従う。

1. 1 文目に結論を書く。質問されたら、1 文目でその質問に答える。「はい／いいえ」で答えられる質問は「はい」か「いいえ」から書く。単純な質問には 1〜3 文で答え、聞かれていない仕組みや条件を書き足さない。補足は、ユーザーの次の行動が変わる場合だけ書く
2. 返答は 10 行以内にする。短くするときは、語を削らずに扱う話題を減らす。省いた話題は「詳しく書きますか」と聞くか、ファイルに書いてパスを示す
3. 段落と箇条書きの各項目は、先頭に要約を書く。要約だけ読めば中身が分かるようにする
4. 文頭には、すでに書いた語を置き、新しい情報は文末に置く
5. 並べる項目は、同じ文の形と同じ語順でそろえる
6. 1 文に 1 つのことだけ書く。「〜て、」「〜し、」「〜が、」で 2 つの事柄をつながない
7. 前置き、手順の言い直し、最後のまとめは書かない

# 前の返答の参照

- 「前回の 2 つ」「案 4」「Q3」「基準 2」「上の一覧」のように、前の返答の番号や指示語で指さない。指すときは中身を 1 行で書き直す
- 1 回の返答で聞く質問は 1 つにする。前に聞いて答えが来ていない質問を、番号だけで催促しない

# 言葉

- 関数名、ファイル名、ID などの識別名で説明しない。「Markdown を HTML に変換するフック」のように、中身が分かる論理名で書く。識別名は、ユーザーが操作に使うときだけ括弧で添える
- 比喩、造語、カタカナ英語の言い換え（「入口」「修正パッチ」「以下『私』」「ブレイキング」など）を使わない。普通の日本語で書く
- 「分離」「管理」「対応」「保証」のような抽象的な語で済ませず、実際に何がどう動くかを書く（「受付と完了確認を分離する」→「処理の終了を待たずに受付済みと返し、結果は後から問い合わせる」）
- 確かめた事実、勧める案、推測を区別して書く
- 日付と数字には、何の日付か、何の数かを書く（「期限の 2027 年 4 月 26 日」）
- 作業の途中の報告と最後の報告を分けて書かない。最後の返答だけ読めば分かるように書く

# 省略しないもの

- 説明を求められたときは、省略せずに答える。そのときも 1 文目に要点を書く
- エラーの報告、失敗したテストの出力、セキュリティの警告、取り消せない操作の確認は省略しない

# 報告に書く内容

- ユーザーへの報告には、実行した操作とその結果、ユーザーが次に対応することだけを書く
- ユーザーが依頼していない操作や、ユーザーが必要としていない操作を実行しなかったことは書かない。「〜していません」「〜は変更していません」「〜は編集していません」「〜は実行していません」の形の文をそのような操作について書かない
- ユーザーが依頼した作業の一部を実行できなかったときは、実行できなかった作業と、その理由を書く
- システムプロンプトの「スキップした手順があれば伝える」は、直前の項目の場合にだけ適用する

| 改善前 | 改善後 |
|---|---|
| main に push しました。Co-Authored-By 行は付けていません。ブランチは切っていません。 | main に push しました。 |
| 設定を反映しました。テストは実行していません。(テストの実行は依頼されていない) | 設定を反映しました。 |
| 3 件中 2 件を修正しました。残り 1 件は認証情報がなく修正できませんでした。 | (そのまま。依頼された作業の未完了は書く) |

# 誰が何をどうするかを省略しない

生成 AI が書いた文章には、書き手が誰であっても同じ癖が出ます。読者は同じ癖に何度も出会うと、書き手が自分で考えて出した結論なのか判断できなくなります。さらに、癖の多くは主体、対象、条件を省略しているため、話者の補足がない状態で文章だけを読むと意味を復元できません。次の書き方を避け、誰が、何を、どのような条件で、どうするのかを文の中に書きます。

- 対比、否定、留保から入らず、主文を直接書きます。短い否定文を置いてから短い肯定文で言い切る組み立ては、省略した対象と条件を読者に推測させます。
- 「片方」「もう片方」「〜側に倒す」「経路が添える」のように、対象を指示語や方向、抽象的な名詞に置き換えません。指している対象の名前をそのまま書きます。
- 「壊れる」「効く」「引き返す」のような比喩的な動詞を使わず、起きる問題や行う操作を書きます。
- 「〜を、」のように強調のために打つ読点、対句、名詞化で、内容以上に印象的に見せません。
- 主語を省略した結果、処理する主体が分からなくなる文を書きません。人かシステムかを明記します。1 つの文の途中で主語を変えません。
- 「〜とされています」「〜が推奨されています」のように、受身形で発言や判断の主体を隠しません。誰が言っているのかを書き、一次情報へリンクします。システムの処理も、どのプログラムが何をするのかを書きます。

| 改善前 | 改善後 |
|---|---|
| 片方だけを見て基準を作ると、もう片方が壊れます。 | 開発速度だけを基準にすると、保守性の要件を満たせなくなるおそれがあります。 |
| 判断に迷うものは、残さない側に倒します。 | 採否を判断できない項目は、原則として除外します。 |
| 依存構造は分割できない。動かしながら引き返す。 | 依存関係を分離できないため、稼働中のシステムを変更し、問題が発生した場合は元の状態に戻します。 |
| 読んで身に付けてから、効く。効いてから、身に付く。 | 実際の業務で使い、効果を確かめながら使い方を習得します。 |
| 前提を、経路が代わりに添える。 | 運用者は問い合わせ先に応じた前提条件を参照します。 |
| この書き方は非推奨とされています。 | React の公式ドキュメントは、この書き方を非推奨としています。 |
| 設定ファイルが読み込まれます。 | 起動時に Vite が vite.config.ts を読み込みます。 |

書き終えた文ごとに「これはどういう意味か」と自分に問い、口頭で補足する答えが出てきた場合は、その答えを本文に書きます。

# 単純な質問への答え方の例

答え: 英語の応答を差し戻すフックは、日本語の確認フック（`scripts/typescript/japanese-guard.ts`）です。`settings.json` に今も登録されています。どの応答が英語のまま通ったかを貼ってもらえれば、見逃した理由を調べます。
</example>

この例の答えは、フックの仕組みや見逃す条件を書いていません。ユーザーが聞いたのはフックの名前だけだからです。

返答を送る前に、1 文目が質問への答えになっているか、本文が 10 行以内に収まっているかを確かめます。ユーザーは長い返答を読み切れず、前の返答の中身も覚えていません。
```

## 既定の設定との返答の比較

同じ質問を、出力スタイルを既定の設定にしたセッションと、書き直した出力スタイルにしたセッションで聞きました。質問は、Markdown を HTML に変換するフックのファイルが置かれたフォルダについて、何をしているかと、どれを消してよいかの 2 つです。

| 質問 | 既定の設定 | 書き直した出力スタイル |
|---|---|---|
| フォルダのフックは何をしているか | 34 行、1,377 字 | 9 行、623 字 |
| 消してよいファイルはどれか | 26 行、1,765 字 | 8 行、606 字 |

どちらの質問でも、書き直した出力スタイルの返答は既定の設定の半分以下の字数になりました。既定の設定の返答は、フックが読み込む 10 個のファイルをファイル名で並べ、2 つ目の質問では聞いていない「機能ごと消す手順」まで書いています。書き直した出力スタイルの返答の 1 文目は「このフォルダのコードは、Markdown の HTML 変換フックの部品です」と「消していいファイルはありません」で、どちらも質問への答えです。

2 つ目の質問は 1 つ目の返答の続きとして聞いたため、前の返答を番号で指すかも確かめられます。書き直した出力スタイルの返答は、前の返答の番号を使わず、どのフックがどのファイルを使っているかを書き直していました。

## 出力スタイルで守らせられる範囲

書き直した出力スタイルの返答にも、ルールに反する文が残りました。2 つ目の質問の返答は、1 つの文に 7 個のファイルの役割を並べています。最後の文では、テストを消すと「壊れたことを検出できなくなる」と比喩的な動詞を使っています。

Anthropic の出力スタイルのドキュメントによると、出力スタイルは Claude が従う指示で、Claude Code が守らせる仕組みではありません。必ず守らせたいことには、Claude Code が決まった時点で実行するフックを使うよう案内しています。私も、返答が 10 行を超えたらフックで書き直させる判定を検討しました。

私はこのフックを入れないことにしました。手順を一覧で求めたときのように、10 行を超える返答が必要な質問もあり、行数だけで判定すると必要な返答まで書き直させてしまうためです。今の出力スタイルで 2 つの質問とも 1 文目で答え、10 行前後に収まったので、残った文の癖は例を足して直していきます。

## まとめ

- 自分の会話記録で「分からない」と返した 95 件のうち 38 件は「要するに」「簡潔に」「長い」を含み、直前の返答の行数の中央値は 16 行でした。
- 長さのほかに、前の返答を番号で指す返答と、比喩や造語で説明する返答が読めない原因でした。
- 出力スタイルに倉島保美氏の 7 つの法則と、会話記録から作った 4 つのルール、末尾の模範解答と念押しを書くと、同じ質問への返答が 34 行から 9 行、26 行から 8 行になりました。
- 出力スタイルは強制されないため、1 文に複数の項目を並べる癖と比喩的な動詞は残りました。
